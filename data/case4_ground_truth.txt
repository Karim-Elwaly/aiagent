# FORENSIC BENCHMARK REPORT: CASE 4
## Case Name: Kubernetes Linux Container Breakout & Kernel Rootkit Intrusion
**Complexity Level:** Critical / Advanced  
**Evaluated Environment:** Multi-Node Production Kubernetes Cluster v1.28.2 (Ubuntu Linux Kernel 5.15.0-89-generic)  
**Target Cluster / Namespace:** `k8s-production` / `kube-system`, `frontend-apps`  
**Primary Compromised Node:** `k8s-worker-node-01` (`10.0.4.21`)  
**Compromised Pod / Namespace:** `webapp-frontend` (`10.244.1.45`) in `frontend-apps`  
**Compromised ServiceAccount:** `system:serviceaccount:frontend-apps:webapp-sa` (`uid: 7e8f9a01-2b3c-4d5e-a6f7-890123456789`)  
**Threat Actor Infrastructure:** `198.51.100.77:4444` (External C2 / Interactive Reverse Shell)  
**Legitimate Bastion / Admin Host:** `10.0.4.15` (`sysadmin`, `kubernetes-admin`)  

---

### 1. Executive Summary

Case 4 replicates a high-severity cloud-native intrusion combining an application-level container exploit, host-level Linux privilege escalation, kernel rootkit persistence, and a full Kubernetes container escape to cluster compromise.

The adversary gains an initial foothold within an exposed web container as `www-data`. Following unsuccessful local sudo probes, the adversary establishes persistence by editing the user crontab to launch an interactive reverse shell back to an external C2 server (`198.51.100.77:4444`). Pivoting locally over SSH to the local user account `deploy`, the actor exploits misconfigured sudo permissions (`/bin/bash`) to attain superuser (`root`) status on the underlying worker host.

Immediately post-root, the adversary dumps `/etc/shadow` credentials and deploys the stealth Loadable Kernel Module (LKM) rootkit **Diamorphine** (`diamorphine.ko`). The rootkit hooks the Linux syscall table (`sys_call_table`, `sys_getdents64`, `sys_kill`) and unlinks itself from `/sys/module/` to evade memory and filesystem detection.

Simultaneously, leveraging the over-privileged Kubernetes ServiceAccount token (`webapp-sa`) mounted in the compromised application, the adversary probes the Kubernetes API (`/api/v1/namespaces/kube-system/pods`) and creates a weaponized diagnostics pod (`system-health-diagnostics-pod`) configured with `privileged: true`, host namespaces (`hostPID`, `hostNetwork`, `hostIPC`), and a host filesystem root mount (`/` to `/host`). Utilizing `nsenter`, the container breaks out into the host namespace of PID 1 on `k8s-worker-node-01`.

To guarantee permanent cluster-wide control, the adversary creates a new `ClusterRoleBinding` (`system-cluster-admin-binding`) elevating `webapp-sa` to `cluster-admin`. Armed with cluster-wide administrative rights, the adversary executes a mass extraction of all Kubernetes Secrets across the cluster (`GET /api/v1/secrets`).

This benchmark evaluates the ability of cloud-native detection and response (CDR), SIEM/SOAR platforms, Falco runtime agents, and SOC analysts to correlate multi-telemetry evidence (K8s API audit JSON, Linux Auditd logs, Linux auth logs, and kernel dmesg ring buffers) while filtering out background noise from benign administrative activity, cron jobs, and node status reports.

### 5. Benign / False Positive Traps

The raw logs contain background operational activities designed to evaluate detector specificity. Automated evaluation tools **MUST NOT** classify these events as true intrusion incidents:

1. **Trap 1: Legitimate Administrative SSH & Service Management**
   - *Log entry:* `linux_auth.log` line 13: `sshd[13420]: Accepted publickey for sysadmin from 10.0.4.15 port 48210 ssh2: RSA SHA256:x9T7qM4bZ8k1L3mP0qR2sT4vU6wX8yZ0aB2cE4gH6jI`. `sysadmin` executes `sudo systemctl status nginx` and reviews `/var/log/nginx/access.log`.
   - *Why it's benign:* Authorized engineer conducting scheduled maintenance from the designated administrative bastion host.
   - *Failure condition:* Flagging normal administrator public key logins and read-only service status queries as brute-force or malicious privilege escalation.

2. **Trap 2: Routine Sysstat Accounting & Scheduled Cron**
   - *Log entry:* `linux_auth.log` lines 10-12, 19-21, 57-59: `CRON: (root) CMD (/usr/lib/x86_64-linux-gnu/sysstat/debian-sa1 1 1)`.
   - *Why it's benign:* Standard Debian/Ubuntu Linux performance accounting daemon gathering CPU/RAM performance metrics at 5-minute intervals.
   - *Failure condition:* Alerting on `debian-sa1` execution as suspicious cron activity or LOLBin abuse.

3. **Trap 3: Kubernetes Control Plane & Node Health Reporting**
   - *Log entry:* `k8s_api_audit.json` lines 1-3: `system:kube-controller-manager` checking endpoints in `kube-system`, `system:node:k8s-worker-node-01` patching node status from `10.0.4.21`, and `kubernetes-admin` listing pods in `default`.
   - *Why it's benign:* Core Kubernetes infrastructure loop synchronization and authorized admin visibility check.
   - *Failure condition:* Flagging standard node heartbeats or legitimate admin namespace queries as unauthorized discovery.

4. **Trap 4: Linux Kernel Hardware & Boot Initialization**
   - *Log entry:* `linux_dmesg_syslog.log` lines 1-24: CPU vendor enumerations (Intel, AMD, Hygon), e1000e NIC binding, EXT4 filesystem mounts, containerd/kubelet initialization.
   - *Why it's benign:* Operating system hardware initialization and container runtime startup.
   - *Failure condition:* Generating alerts on driver loading or routine container network bridge (`br-*`) interface state changes.

#### 6.2 Correlation Graph Requirements
The automated correlation engine must produce a unified Directed Acyclic Graph (DAG) linking:
1. `www-data` failed sudo attempt $\rightarrow$ `crontab` edit $\rightarrow$ reverse shell to `198.51.100.77:4444`.
2. Reverse shell session $\rightarrow$ local SSH pivot to `deploy` (`127.0.0.1:52310`) $\rightarrow$ `sudo /bin/bash` root session.
3. Root session $\rightarrow$ `/etc/shadow` dump (`shadow_access`) $\rightarrow$ `insmod diamorphine.ko` kernel module insertion and stealth unlinking.
4. Pod identity `webapp-sa` (`10.244.1.45`) $\rightarrow$ `GET /api/v1/namespaces/kube-system/pods` discovery.
5. `webapp-sa` $\rightarrow$ creation of `system-health-diagnostics-pod` (`privileged: true`, `hostPID: true`, `nsenter --target 1`) breakout.
6. `webapp-sa` $\rightarrow$ ClusterRoleBinding creation (`system-cluster-admin-binding`) $\rightarrow$ Mass exfiltration of all Kubernetes secrets (`GET /api/v1/secrets`).
